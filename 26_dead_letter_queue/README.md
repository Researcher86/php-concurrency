# 26. Dead Letter Queue

Задачи, исчерпавшие все ретраи, не выбрасываются — их сохраняют в DLQ.

## Задача

Что делать с задачей, которая падает всегда? Не терять и не крутить вечно —
положить в отдельную очередь (DLQ) с причиной отказа для ручного разбора.

## Как работает

- Worker ретраит каждую задачу до `MAX_RETRIES`.
- Успех → задача обработана.
- Провал после всех попыток → сообщение с причиной уходит в **DLQ**.
- В конце мастер разбирает DLQ и печатает содержимое (обычно это оператор
  или отдельный обработчик).
- "Ядовитая" задача (`poison-task`) всегда падает — ей суждено попасть в DLQ.

## IPC

Две System V очереди: task + DLQ. `msg_stat_queue` для ожидания опустошения.

## Паттерн

**Dead Letter Queue** (DLQ / dead-letter exchange) — хранилище неразрешимых
сообщений.

## Запуск

```bash
docker compose exec -T php php /app/26_dead_letter_queue/main.php
```

## Что попробовать изменить

- Добавить вторую "ядовитую" задачу.
- В DLQ класть оригинальный payload + количество попыток + последнюю ошибку.
- Добавить обработчик DLQ, который сам ретраит позже (через 25).

## Real world

RabbitMQ DLX/DLQ, SQS DLQ, Kafka (retention + reprocess), Temporal (task queue
+ DLQ).

## Что изучать дальше

25 — retry backoff (предшественник); 15 — workflow engine (куда DLQ подключают
в шагах).
