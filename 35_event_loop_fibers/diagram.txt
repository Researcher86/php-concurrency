Event Loop + Fibers (фибры как coroutine поверх event loop)

   фибры регистрируют интерес:                 event loop:
   ┌─────────────────┐   suspend(['read', $s1])   ┌──────────────────────┐
   │ fiber#0 (read)  │───────────────────────────►│                      │
   │ fiber#1 (read)  │───────────────────────────►│  stream_select()     │
   │ heartbeat(timer)│───────────────────────────►│  ждём read-ready ИЛИ │
   └─────────────────┘   suspend(['timer',$at])   │  наступившего таймера│
        ▲                                         │                      │
        │  resume('ready'/'tick')                 └──────────┬───────────┘
        └────────────────────────────────────────────────────┘
   Протокол: фибра САМА сообщает loop через suspend, что ей нужно.
   loop спит в select() до первого готового события и будит те фибры,
   чьё событие наступило. Остальные продолжают "спать".

   Ключевое: фибры НЕ опрашивают. Они ждут — будит их select.
   Это тот же event loop из урока 18, но обработчики обёрнуты в фибры,
   и у каждой — свой стек вызова (можно писать последовательный код).

   ⚠ Блокирующий read внутри фибры по-прежнему останавливает loop:
   фибры кооперативны, а select() мультиплексирует готовность — нельзя
   внутри фибры делать fgets() на неготовом сокете (урок 36).
